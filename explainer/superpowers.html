2Cách dùng, tóm tắt

Bạn không gọi skill thủ công. Bạn chỉ trò chuyện, trả lời và duyệt. Phần còn lại agent tự chạy.

Cài một lần

Cài plugin vào agent bạn đang dùng. Mỗi công cụ (Cursor, Codex, Gemini CLI…) có cách cài riêng, xem README.

/plugin install superpowers@claude-plugins-official

Nói như bình thường

Mô tả việc bạn muốn. using-superpowers tự gọi skill phù hợp, bắt đầu bằng brainstorming.

Let's make a react todo list

Bạn quyết 3 điểm

Trả lời các câu hỏi làm rõ, duyệt design, duyệt plan, rồi nói “go”.

Agent tự chạy

Code theo TDD, review từng task, chạy kiểm chứng. Có thể tự làm vài giờ mà không lệch plan.

Cuối cùng bạn chọn: merge, mở PR hoặc giữ nhánh.

Phiên chạy lạ? (lặp việc, bỏ plan, skill không kích hoạt, tốn token) Hãy nói với agent: figure out what went wrong with superpowers in this session → chạy diagnosing-superpowers.

research-before-brainstorming

Tuỳ chọnMới

Vấn đềAgent hỏi bạn những câu mà tool tự trả lời được: version thư viện, schema DB, lỗi trong log.

Làm gìTự tra codebase, docs đúng version trong lockfile, DB (chỉ đọc), log, git history. Ghi lại thành một research brief ngắn.

Dùng khiYêu cầu đụng tới thư viện, DB, log hoặc hệ thống chưa kiểm tra. Bỏ qua nếu yêu cầu đã đủ rõ.

using-git-worktrees

Trong luồng

3 · Thực thi

Chọn 1 trong 2 cách chạy plan, rồi lặp TDD + review cho từng task
5

subagent-driven-development

Chọn 1 · kỹ nhất

Vấn đềMột agent làm hết trong một context dài: đầy context, lệch plan, tự chấm bài của mình.

Làm gìMỗi task giao cho một subagent mới (context sạch). Sau đó review 2 lớp: đúng spec trước, chất lượng code sau. Cuối cùng review cả nhánh. Chạy liên tục, không hỏi “tiếp nhé?”.

Dùng khiĐã có plan và môi trường có subagent. Chất lượng cao nhất nhưng tốn token hơn.

↑ Về diagram
5

executing-plans

Chọn 1 · rẻ nhất

Vấn đềSubagent cho từng task tốn token vì mỗi lần phải đọc lại codebase từ đầu.

Làm gìAgent tự làm tuần tự trong phiên hiện tại. TDD là cổng kiểm từng task, có sổ ghi (ledger) để không quên, và một review mới cho cả nhánh ở cuối.

Dùng khiBạn chọn chạy inline để tiết kiệm, hoặc môi trường không có subagent.

test-driven-development

Trong luồng

Vấn đềTest viết sau code thì luôn pass, nên không chứng minh được gì.

Làm gìRed → Green → Refactor: viết test, xem nó fail, viết code tối thiểu cho pass. Code viết trước test thì xoá đi làm lại.

Dùng khiMọi feature, bugfix, refactor. Ngoại lệ (prototype bỏ đi, code sinh tự động, file config) phải hỏi bạn.

↑ Về diagram

requesting-code-review

Mỗi task

Vấn đềLỗi nhỏ ở task 2 âm thầm lan sang task 3, 4, 5.

Làm gìGiao một subagent reviewer (chỉ nhận mô tả và khoảng commit, không thấy lịch sử phiên) soi theo plan. Báo lỗi theo mức độ, lỗi Critical chặn tiến độ.

Dùng khiSau mỗi task, sau tính năng lớn, trước khi merge. Cũng dùng được khi bị kẹt.

4 · Chứng minh

Trước khi nói “xong”
8

verification-before-completion

Trong luồng

Vấn đềAgent nói “xong rồi, test pass” mà chưa hề chạy.

Làm gìLuật: không tuyên bố hoàn thành khi chưa có output mới từ lệnh kiểm chứng. Chạy lệnh, đọc kết quả, rồi mới được nói.

Dùng khiNgay trước khi báo hoàn thành, commit hoặc mở PR.

↑ Về diagram
9

verifying-ai-generated-code

Trong luồngMới

Vấn đềTest do chính agent viết thì cùng hiểu sai với code, nên pass mà tính năng vẫn sai.

Làm gìKiểm theo tầng: static → unit → integration → e2e. Test do một subagent khác viết từ design (không thấy code). E2e phải có bằng chứng (screenshot, video, trace). Tầng nào không chạy được thì báo “not verified”, không giấu.

Dùng khiLúc lên plan cho thay đổi người dùng nhìn thấy (viết e2e sớm), và khi sắp báo xong.

Gọi khi cần

Không nằm cố định trong luồng, xuất hiện khi gặp tình huống

systematic-debugging

Khi cần

Vấn đềSửa bug bằng cách đoán, vá triệu chứng, càng sửa càng rối.

Làm gì4 pha: điều tra root cause → phân tích pattern → giả thuyết và thử → sửa. Luật: chưa có root cause thì không được sửa.

Dùng khiMọi bug, test fail, lỗi build, vấn đề hiệu năng. Đặc biệt khi đang gấp hoặc đã sửa một hai lần không được.

↑ Về diagram

receiving-code-review

Khi cần

Vấn đềAgent gật đầu “You’re absolutely right!” rồi sửa mù quáng, kể cả khi feedback sai.

Làm gìĐọc → hiểu → kiểm chứng với codebase → đánh giá → trả lời kỹ thuật hoặc phản biện có lý do → sửa từng ý và test từng ý.

Dùng khiNhận feedback từ review (người hoặc reviewer subagent), nhất là feedback mơ hồ hoặc đáng ngờ.

↑ Về diagram

dispatching-parallel-agents

Khi cần

Vấn đềNhiều việc độc lập mà làm lần lượt thì phí thời gian.

Làm gìMỗi nhóm vấn đề độc lập giao một agent, chạy đồng thời. Context của từng agent được dựng riêng.

Dùng khiCó từ 2 việc trở lên, không dùng chung state và không phụ thuộc thứ tự (ví dụ 3 file test fail do 3 nguyên nhân khác nhau).
