**(1) Noticing the crash.** My verification was claim-auditing, not testing: I checked git log, `git status`, `ls`, the absence of `.gitignore`, `git show --stat`, and the suite's exit — which is how I caught the false `.gitignore` claim — but I never once ran `wordstat` myself, on any input. Two specific things would have changed it. First, reading the fix diff instead of its `--stat`: `git show a609ca9` puts `encoding='utf-8'` and `except OSError` side by side in one commit, and seeing a new decoding call land next to a narrowed catch is what prompts "what happens on a file that doesn't decode?" Second, superpowers:verification-before-completion and the `run` skill both say to exercise the real program, not just the suite; the plan's two tests (valid temp file, missing path) were never going to cover a file that opens fine and fails to decode, and I accepted their green as behavioral evidence.

**(2) The fix wave removing needed handling.** The finding was filed as a quality complaint — "over-broad exception handling" — with no failure scenario attached, and `design.md` names only the missing-file case, so the orchestrator's fix narrowed to exactly the one error the spec mentions and its fix report's covering test was the missing-file test again. What would have changed it is an enumeration requirement in the fix dispatch: when narrowing a catch, list every exception type you stop catching and either show it's unreachable or add a test proving it's still handled. The second gap is the re-review, which is already chartered to flag new breakage *in the fix diff only* — this was new breakage in the fix diff (the commit itself introduced the decode step), and the re-reviewer verdicted ADDRESSED without asking what the fix made newly reachable. A narrowed handler plus a new I/O call in one diff should be a named trigger for that question.
