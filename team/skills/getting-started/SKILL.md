# Getting Started

Orient a new team member on how to work with Claude Code effectively here.
This skill **teaches** — it creates no files and changes nothing. It gives
the mental model, then points at the team's own workflow and the tools
that carry it.

## When to Use

Run this on someone's first sessions, or whenever a member wants to
understand *how* to work with the agent rather than get a specific task
done. It's an orientation, not a task — keep it short.

## The Mindset

**You're working with an agent, not a search box.** The agent is most
effective when you give it a goal and enough context to reason, then let
it work — not when you hand it one under-specified instruction at a time.
Think of it as a capable teammate who is new to *your* codebase: it brings
strong general skill, you bring the local knowledge.

**Match the mode to the task:**

- **Brainstorm first** when the shape of the work is still open — a new
  feature, a design decision, anything where "what should we build?" isn't
  settled. Say so, or just describe the goal and the agent will reach for
  `superpowers:brainstorming`.
- **Plan** when the *what* is clear but it's multi-step — the agent writes
  a plan (`superpowers:writing-plans`) you review before any code.
- **Implement** when the plan or the change is small and well-understood —
  the agent builds it, test-first where it matters
  (`superpowers:test-driven-development`).
- **Debug** when something's broken — describe the symptom and let it work
  the problem systematically (`superpowers:systematic-debugging`) rather
  than guessing at fixes.

A good default for anything non-trivial: **brainstorm → plan → implement →
review.**

## Why Skills Exist

Skills are packaged, reusable procedures — the team's accumulated "how we
do X" made executable. Two things to know:

- **They auto-trigger.** Each skill has a description that says *when* it
  applies. You usually don't invoke them by hand — you describe your
  situation and the right skill fires. That's why describing the goal
  well matters more than naming a skill.
- **You can invoke them explicitly** when you want to:
  - **Team skills** — `/<team>:<name>` (this team's shared, committed
    skills).
  - **Personal skills** — `/<name>` (yours alone, under
    `~/.claude/skills/`, not shared with the team).

To build your own: `/new-skill` (a technique), `/new-workflow` (an ordered
multi-step flow), or `/new-connector` (wire in a doc, MCP tool, or
convention).

## Where the Team's Flow Lives

This team's canonical working flow is in **`team/workflow.md`** — read it.
It's the composition of engine and team skills tailored to how *this* team
actually works, generated from the team intake. When in doubt about "how
do we do things here," that file is the answer, and `/getting-started`
(this skill) is the map to it.

**If `team/workflow.md` doesn't exist yet**, this team hasn't finished
setup — the file is generated, not shipped. Don't send the member looking
for a file that isn't there. Instead tell them so plainly and point at the
one-time setup path: a leader runs `/team-setup` (interview → `team/intake/`)
then `/generate-workflow` to produce it. Until then, the general mindset
above plus the raw Superpowers engine skills are what's available.

## Quick Reference

| Situation | Reach for |
|---|---|
| Shape of the work is still open | brainstorm (`superpowers:brainstorming`) |
| Clear but multi-step | plan (`superpowers:writing-plans`) |
| Small, well-understood change | implement, test-first |
| Something's broken | debug systematically |
| "How does this team do X?" | read `team/workflow.md` |
| Build your own tooling | `/new-skill`, `/new-workflow`, `/new-connector` |

## Red Flags — Stop and Correct

| Excuse / impulse | Reality |
|---|---|
| "Let me set up their workflow file for them" | This skill teaches only. `team/workflow.md` is generated by `/team-setup` + `/generate-workflow`, not here. |
| "I'll just tell them to memorize the skill names" | Skills auto-trigger from descriptions. Teach them to describe the goal well; explicit invocation is the exception. |
| "No need to mention Superpowers" | Always credit upstream. The engine is Superpowers (obra), MIT — point them at the source. |
| "Skip the team workflow, the general mindset is enough" | The whole point is `team/workflow.md` — the team's *own* flow. Orientation that doesn't land them there is incomplete. |
| "`team/workflow.md` is missing — I'll just generate it for them" | Missing file means setup hasn't run. This skill teaches only. Tell them to run `/team-setup` then `/generate-workflow`; don't generate it here. |
